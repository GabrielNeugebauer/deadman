# Deadman security audit (2026-10-08)

Scope: the working tree of `feat/safety-net-mvp-02-10-2026`, three days after the [10-05 audit](security-audit-2026-10-05.md).

- **On-chain:** the Anchor program `onchain/programs/deadman` (program id `ACHVLMoLDM3YPpGbNST4cZW4Tf2jx6nzJGuusyLJHofL`, Anchor 1.1.2, 23 handlers), tested against the current `target/deploy/deadman.so`.
- **Off-chain:** the four open 10-05 Medium findings (M-1..M-4) in `lib/`, `tool/kora_gateway.dart` and `tool/keeper.dart`, plus the new decoy-wallet duress mode and the Jupiter token picker.

Method: six lanes ran in parallel, and each lane's findings were then checked by an independent verifier who re-read the code and re-ran the tests.

| Lane         | What it did                                                                                                                              |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| fuzz         | Stateful Trident 0.12 fuzz suite (`onchain/trident-tests/fuzz_0`), 17 flows, 9 invariant families                                        |
| qedgen       | qedgen 2.51.0 probe, a `.qedspec` of the vault state machine, generated proptest, and random-sequence property tests on the real program |
| lifecycle    | `/audit-solana` checklist on create, update, guard, pulse, lockdown, unlock, revoke, close and legacy recovery                           |
| funds        | `/audit-solana` checklist on every instruction that moves value, plus Token-2022 mints, NFT tiers and `remaining_accounts`               |

| offchain     | Re-check of M-1..M-4 and review of duress mode and the token picker                                                                      |

The audit changed no production code. It added test files only (listed under [Tools run](#tools-run)). Nothing was built with `anchor build`, deployed or sent to any cluster, and no keypair or `.env` file was read.

Every finding below has a test. A test that shows a defect asserts the correct behaviour and is marked `#[ignore]` (Rust) or `skip:` (Dart), so the default suites stay green. The command to run it is given with each finding.

## Medium findings (carried over)

### M-2 [Medium] The web build still stores claim keys, the phrase, the guard key and PIN hashes next to their AES key in localStorage

- **Where:** `lib/state/secure_store.dart:57` (`const FlutterSecureStorage()` with no `WebOptions`); `lib/state/actions.dart:39` (`if (web) return true;` in the biometric gate); `lib/ui/screens/settings_tab.dart:382-530` (`_ReceivePrivatelyCard`); `web/index.html` (no CSP).
- **Description:** unchanged since 10-05. No `WebOptions` or `wrapKey` exists anywhere in `lib/`. `pubspec.lock` still resolves `flutter_secure_storage_web` 2.1.1, which generates an extractable AES-GCM key and stores `exportKey('raw')` in localStorage next to the ciphertexts. The web build still offers receiving profiles, phrase reveal and restore.
- **Evidence:** `test/security/offchain_test.dart`, two skipped tests. With `isWebProvider = true`, `saveClaimProfile(Rail.cloak, addr)` succeeds and writes `recovery_phrase`; the CSP check finds no policy. Run: `flutter test test/security/offchain_test.dart --run-skipped --plain-name 'M-2'`.
- **Fix:** refuse receiving profiles, phrase reveal and restore on web, or pass `WebOptions(wrapKey, wrapKeyIv)` derived from the PIN with a slow KDF. Add a strict CSP to `web/index.html`.

### M-3 [Medium] Sybil guards can still exhaust the sponsor's shared global quota and block duress lockdowns for 24 h

- **Where:** `tool/kora_gateway.dart:1324` (`final quota = claim == null ? limiter : claims;`), `:1137-1165` (`UsageLimiter.check`, global cap checked first at `:1144`), `:1963-1985` and `:2035-2065` (caps), `:1863-1885` (margin pricing, no floor); `lib/solana/deadman_client.dart:2495-2503` (`_shouldFundGuard`), `:2541-2565` (guard-paid fallback).
- **Description:** unchanged since 10-05. The gateway diff only adds `subscribe_with_token` and denies `set_subscription_price`. Pulses and lockdowns share one limiter, and attacker guards on genuine vaults pass every check. With production caps (per vault 24, per signer 48, global 2000), about 84 attacker vaults fill the day's budget. A token-fee owner's guard may hold no SOL, so the guard-paid fallback can fail.
- **Evidence:** skipped test drives the real `SponsorRoute.admit` with `UsageLimiter(global: 5)`. Five Sybil guards pulse their own vaults, then the victim's lockdown gets `GatewayRejection: Rate limit: the sponsor reached its cap of 5 sponsored transactions per 24h`. Run: `flutter test test/security/offchain_test.dart --run-skipped --plain-name 'M-3'`.
- **Fix:** a separate (uncapped or much larger) lockdown budget; budget in lamports spent rather than transaction count, favouring established vaults; a mainnet per-tier minimum fee; a SOL stipend for the guard even for token-fee owners, or a paymaster fallback when the sponsor refuses a lockdown.

### M-4 [Medium] The keeper still pays a network fee for every installment release, however small

- **Where:** `tool/keeper.dart:252` (`if (installments || fullyVested || lastRelease == null) return true;`), `:143-158` (`decideSol`), `:196-238` (`decideToken`, executes at `:218` once both token accounts exist), `:493-530` (`_sweepVesting`); `constants.rs:37` (`MIN_VEST_PERIOD_SECS = 60`).
- **Description:** only comments changed in `keeper.dart`. Installments bypass `--vest-interval`, `decideSol` executes a 1-lamport release with fee 0, and `decideToken` executes before it reads any price. The verifier rejected the lane's claim that the Jupiter picker widens the attack: the program has no mint allowlist, so an attacker could already vest any mint by calling the program directly. The picker only makes accidental dust easier for honest owners.
- **Evidence:** three skipped tests. `vestingReleaseDue(claimable: 1, installments: true, lastRelease: now - 60, interval: 86400)` returns `true`; `decideSol(vestingAsTier(rule, 1), ...)` and `decideToken` (no price, claimable 1) both return execute. Run: `flutter test test/security/offchain_test.dart --run-skipped --plain-name 'M-4'`.
- **Fix:** execute only when `fee × price ≥ 5000 + priority` lamports or the payout exceeds a configured minimum; throttle installments per schedule like continuous vesting (except the last one); cap work per sweep and order it by value.

## Low findings

### SUB-M1 [Low] `subscribe` and `subscribe_with_token` have no maximum amount, so a price change in flight can charge the owner up to their whole token balance

The ID is kept from the lane (and its test names); the verifier lowered the severity from Medium to Low.

- **Where:** `onchain/programs/deadman/src/instructions/subscription.rs:109-130` (`handle_subscribe`), `:245-285` (`handle_subscribe_with_token`); price setters `:34-57` and `:169-188`; client `lib/solana/deadman_client.dart` `buildSubscribe` (around `:607-656`).
- **Description:** the charge is `price_per_period × periods` (and `burn_bps` for token pricing), read from the config accounts when the transaction executes. The only argument is `periods`. The setters accept any price above 0 and any `burn_bps ≤ 10000`, with no bound and no timelock. The client checks `held ≥ cost` when it builds the transaction but never puts `cost` on-chain, so the window runs from signing to landing. An admin repricing (honest, mistaken or malicious), or a gateway that holds owner-signed transactions and reprices first, charges whatever the new price is, up to the owner's balance.
- **Severity reasoning:** only the admin can trigger it. Under MAINNET.md option B the admin is also the upgrade authority, which can already do anything, so nothing new is exposed: **Low**. Under MAINNET.md option A after step 6, the deploy key stays fee admin without upgrade rights. There this flaw lets it go beyond the documented 5% fee cap and drain every subscriber whose UI showed an older price: **Medium**.
- **Evidence:** `onchain/programs/deadman/tests/review_subscription.rs`, two ignored tests. The owner's instruction is built at a price of 5,000,000, the admin reprices, and the owner's transaction lands: "owner signed for 5000000, was charged 5000000000" (USDC) and "owner signed for 5000000, lost 5000000000" (token, `burn_bps` raised to 10000). Run: `cd onchain && cargo test -p deadman --test review_subscription sub_m1 -- --ignored`.
- **Fix:** add `max_amount: u64` to both instructions with `require!(amount <= max_amount)`, and have the client pass `terms.cost(periods)`. For `subscribe_with_token`, also bind `max_burn_bps` (or treat `max_amount` as the cap on transfer plus burn). Optionally bound or timelock price changes.

### SUB-L1 [Low] `set_config` accepts a sysvar as treasury; every SOL payout and SOL vesting release then fails, including fee-waived ones

- **Where:** `onchain/programs/deadman/src/instructions/config.rs:30-37` (`validate_config`), `:68-80` (`handle_set_config`); `instructions/funds.rs:216` (`#[account(mut, address = config.treasury)] treasury`).
- **Description:** `validate_config` rejects only `Pubkey::default()`. The runtime demotes a sysvar account to read-only, so the `mut` constraint on `ExecuteSolRule.treasury` fails with `ConstraintMut` (2000). The constraint is checked before the fee is known, so subscribed (fee-waived) owners are blocked too. `release_vested_sol` and claims of a skipped tier's reserve use the same accounts and stall as well. No funds are lost, and the admin can undo it with `set_config`. Token payouts are unaffected.
- **Evidence:** `review_subscription.rs` ignored test `sub_l1_unusable_treasury_is_rejected_or_does_not_block_payouts`: `set_config(treasury = SysvarC1ock…)` is accepted, then `execute_sol_rule` fails with `Custom(2000)` for both subscribed and unsubscribed owners. The control test with a normal treasury passes. Run: `cd onchain && cargo test -p deadman --test review_subscription sub_l1 -- --ignored`.
- **Fix:** take the treasury as an account in `InitConfig`/`SetConfig` and require it to be system-owned and not executable (or at least reject sysvar IDs). Alternatively make the treasury writable only when the fee is above 0.

### FUNDS-1 [Low] Owner withdrawals ignore skipped-tier reserves, so a leftover reservation later takes deposits meant for tiers added afterwards

Merges the qedgen lane's QG-I1 (same root cause, rated Info there).

- **Where:** `onchain/programs/deadman/src/instructions/funds.rs:125-138` (`handle_withdraw_sol`), `:170-187` (`handle_withdraw_token`); `state.rs:353-356` (`committed()` is 0 for inheritance plans), `:516-537` (`reserved_for`, `payout_gross`); doc comment `funds.rs:430-433`; `vault.rs:262-281` (`close_vault`).
- **Description:** `skip_rule` sets aside `reserved` for a skipped tier, and its doc comment says the share "stays claimable by its own beneficiary". The withdrawals subtract only `committed()`, which is 0 for inheritance plans, so the owner can take the reserved share. The reservation itself is never reduced, and `update_plan` keeps the skipped tier as history, so the owner cannot cancel it. Every tier added later computes its payout on `balance − reserved_for(…)`, so the stale reservation takes the owner's later deposits first. `pay_stipend` does subtract the reserve, so the program protects reserves in one place and not the other. Only the owner's own later deposits are affected, and they go to an heir the owner originally named. This extends 10-05 ON-I7.
- **Evidence:** `review_funds.rs` ignored test `funds1_stale_skipped_reserve_outranks_a_tier_added_after_the_owner_returns`. Bob's Fixed 5 SOL tier is skipped (reserved 5 SOL); the owner withdraws all 10 SOL; the owner adds Carol at 100% and deposits 4 SOL; Carol gets `NothingToPay` (`funds.rs:240`) and Bob receives the 4 SOL net of fee. The passing companion `funds1_current_behaviour_skipped_heir_takes_the_new_deposit` pins today's behaviour, and `review_qedgen.rs::owner_can_withdraw_a_skipped_tiers_reserve` shows the withdrawal itself. Run: `cd onchain && cargo test -p deadman --test review_funds funds1 -- --ignored`.
- **Fix:** choose one model and make `close_vault` agree with it. (a) Reserves are committed: subtract `reserved_for(mint, usize::MAX)` in both withdrawals (`FundsCommitted`) and refuse `close_vault` while a reserve is pending. (b) The living owner may reclaim: cap or clear skipped reserves when the owner withdraws or edits the plan, and reword the `skip_rule` comment. Either way, show pending skipped claims in the app.

### ON-L1 [Low, carried over] The stipend bit is not remapped when `update_plan` compacts history, so a new private-rail tier at a reused index gets no gas

Re-confirmed independently by the fuzz lane (FUZZ-1) and the funds lane (FUNDS-2).

- **Where:** `onchain/programs/deadman/src/state.rs:584-657` (`apply_policy` never touches `stipend_paid`); `instructions/funds.rs:44-66` (`pay_stipend`, bit set at `:64`).
- **Description:** `stipend_paid` is indexed by rule position. `apply_policy` moves paid and skipped tiers to the front and appends new tiers, but leaves the bits where they were. A new Cloak or Zcash tier that lands on an index whose bit is set receives its tokens with no SOL to route them. It can only deny a stipend, never pay one twice: the INV-STIPEND safety half held across about 9 million fuzz flows. Scenario A from 10-05 (restarting a completed plan) is gone, because `update_plan` now rejects completed plans; scenario B (the index shift) remains.
- **Evidence:** Trident liveness run (`FUZZ_STIPEND_LIVENESS=1`, 15000×200) fails only with "INV-STIPEND rule 1 of plan N eligible but denied its stipend". Minimal LiteSVM replays: `review_fuzz.rs::fuzz_on_l1_new_private_tier_gets_its_stipend_after_update_plan` and `review_funds.rs::funds2_new_private_tier_at_a_reused_index_gets_its_stipend`; the new claim key holds 0 lamports where 12,000,000 is expected although the vault has spare SOL. Run: `cd onchain && cargo test -p deadman --test review_fuzz -- --ignored`.
- **Fix:** in `apply_policy`, rebuild `stipend_paid`: for each kept history tier now at index j that came from index i, copy bit i to bit j; clear all other bits.

### ON-L4 [Low, carried over] A Token-2022 permanent-delegate mint lets the owner empty a non-revocable vesting plan

- **Where:** `onchain/programs/deadman/src/state.rs:368-429` (`apply_vesting` accepts any mint pubkey); `instructions/funds.rs:303-311` (`InterfaceAccount<Mint>` accepts Token-2022).
- **Description:** the owner creates a mint with themselves as `PermanentDelegate`, vests it, then transfers the vault's tokens out directly through Token-2022. `committed()` still reports them as owed, and `release_vested_token` returns `NothingToPay`. A freeze authority or the Pausable extension blocks releases the same way. Only the client rejects Token-2022 mints.
- **Evidence:** `review_funds.rs` ignored test `funds4_permanent_delegate_cannot_empty_committed_vesting`: Bob's ATA holds 0, expected 980,000, after a fully vested non-revocable schedule. Run: `cd onchain && cargo test -p deadman --test review_funds funds4 -- --ignored`.
- **Fix:** check the mint in `create_vesting`, `release_vested_token` and `withdraw_token`; reject `PermanentDelegate`, `Pausable`, `NonTransferable` and `TransferHook` mints; flag freeze authorities in the client.

### ON-L5 [Low, carried over] With a Token-2022 transfer-fee mint, `rule.paid` and `RuleExecuted.amount` overstate what the beneficiary received

- **Where:** `onchain/programs/deadman/src/instructions/funds.rs:373-401`, `:568-592`, `:606-626`.
- **Description:** `paid` records the amount sent, but Token-2022 withholds its transfer fee at the destination. Vault-side accounting stays consistent (the balance drops by exactly the gross amount). For vesting, an owner who funds exactly `total` leaves the vault short by the inbound fee, so the schedule never reaches its cap and `close_vault` returns `FundsCommitted` until the owner tops it up.
- **Evidence:** `review_funds.rs` ignored test `funds3_t22_paid_matches_what_the_beneficiary_received`: `paid` 980,000 against 970,200 received for a 1% fee mint. The passing test `t22_transfer_fee_mint_is_accepted_and_vault_side_accounting_holds` confirms the vault side. Run: `cd onchain && cargo test -p deadman --test review_funds funds3 -- --ignored`.
- **Fix:** record the received delta (reload the destination after the transfer), or reject `TransferFeeConfig` mints on-chain as the client already does.

### OFF-N1 [Low] The token lookalike check is bypassed by homoglyph or zero-width symbols, so a fake token reads as USDC

- **Where:** `lib/state/assets.dart:88-94` (`isLookalike`), `:99-113` (`rememberToken`); `lib/state/token_list.dart:197-213` (`listedTokenProvider`); `lib/state/nfts.dart:56-66`.
- **Description:** `isLookalike` compares only `symbol.trim().toUpperCase()` with the built-in tokens. A Jupiter-listed token with symbol `USDС` (Cyrillic U+0421) or `USDC` plus a zero-width space is not flagged, so it is stored without the `·<mint>` suffix and shown as "USDC" across the app. On mainnet, a beneficiary's Circle view names unknown plan mints through `listedTokenProvider`, which remembers any supported listed token with no verified or suspicious check. A malicious owner can fund a plan with a worthless token that the heir sees as USDC. The owner's own picker still shows UNVERIFIED and a confirm dialog. Reachable only if Jupiter lists the attacker's mint; the impact is a misleading label, not a loss of funds.
- **Evidence:** `test/security/offchain_test.dart` skipped test "OFF-N1: a homoglyph or zero-width USDC symbol is marked as a lookalike": `isLookalike(addr, 'USDС')` returns false. The ASCII control (`' usdc '` gets the suffix) passes. Run: `flutter test test/security/offchain_test.dart --run-skipped --plain-name 'OFF-N1'`.
- **Fix:** normalise before comparing (NFKC, strip zero-width and format characters, map confusables to ASCII, or reject non-ASCII symbols). In `listedTokenProvider`, keep the mint suffix for any token that is unverified or flagged suspicious.

### OFF-N2 [Low] Under duress, the Private rails check reads the real Zcash receiving profile and sends its claim key to 1Click

- **Where:** `lib/state/private_rails.dart:361-377` (`RailsCheck.zcash`, `loadClaim(Rail.zcash)` at `:362`); reachable from `lib/ui/screens/settings_tab.dart:322-333`.
- **Description:** `RailsCheck.zcash` reads `secureStoreProvider` directly with no duress check. Under duress the decoy's "Receive privately" card shows "Not set up", but the rails check says "… to your u1 address" when the real phone has a Zcash profile. It also sends the real claim key as `refundTo` to NEAR 1Click, linking that key to the device's IP during a duress session. Only a public address leaks, plus a visible tell.
- **Evidence:** skipped test "OFF-N2: the Private rails check reads the real Zcash receiving profile under duress": the captured `claimKeys.single` equals the real claim key. Run: `flutter test test/security/offchain_test.dart --run-skipped --plain-name 'OFF-N2'`.
- **Fix:** under duress, use the decoy's Zcash profile (or a random key and the sample address) in `RailsCheck.zcash`, or route the check through `VaultActions._decoy`.

## Needs verification

Not counted as findings.

1. **Malicious transfer-hook mints.** `vault_transfer` forwards executor-chosen `remaining_accounts` with `is_signer = false`. With no hook, extra accounts move nothing (`review_funds.rs::extra_accounts_cannot_move_other_vault_tokens`, Token and Token-2022). Not tested with a hook mint whose `ExtraAccountMetaList` names the vault PDA as a signer (carried from 10-05).
2. **Pausable, NonTransferable and DefaultAccountState=Frozen mints.** Traced: the program accepts them; tiers would stay stuck or reserved while paused or frozen, and NonTransferable tokens can never leave the vault. Not tested.
3. **Other builtin program IDs as treasury** (Vote, Stake, Config) may also be demoted to read-only on a real cluster (SUB-L1). In LiteSVM 0.10 the System and SPL Token IDs were credited.
4. **Legacy 1140-byte layout** (`3e1fca3`, `skip_grace` present, no `kind`/`rent_payer`): with exactly one rule, a few accounts in roughly 1 in 16k might decode as the current `Vault`. The 996- and 1318-byte layouts reliably fail to decode (tested). Unknown whether any 1140-byte account exists.
5. **History saturation.** `apply_policy` counts unclaimed skipped tiers toward `MAX_RULES = 8` (`state.rs:597-610`). Eight unclaimable skipped tiers would block `update_plan` for good; withdraw and close still work. Probably by design.
6. **Kora gateway pricing with a pre-funded plan address** (LC-I1 off-chain angle). `tool/kora_gateway.dart` was not checked.
7. **NFT name spoofing.** `rememberNft` (`lib/state/assets.dart:70-79`) has no lookalike check, so an NFT named "500 USDC" would display that way. Whether plan cards add enough context was not checked.
8. **Jupiter decimals are trusted** for parsing user input (`rememberListedToken`). A wrong value from the API or a `JUP_TOKENS_URL` override would fund 10^k too much or too little. Not reproduced.
9. **Duress traces.** Picking a token under duress writes `listed_tokens_v1` to SharedPreferences, and viewing plans sends their mints to `lite-api.jup.ag`. Privacy notes only.

**The program is close to ready for an external audit; the app, gateway and keeper still carry three Medium findings.**

- **On-chain:** no Critical, High or Medium findings, and fuzzing found no break in the core money invariants. Before mainnet:

  - carried over: restrict or remove `recover_legacy_vault` (ON-L2) and move the admin and upgrade authority to a multisig with a timelock (ON-I4).

## Resolution (2026-10-08)

Fixed on the same branch after the audit. The owner also changed the business model: **the subscription is removed completely** (no Plus plan, no `Subscription`, `SubscriptionConfig` or `SubscriptionPrice` accounts, no `subscribe`, `subscribe_with_token`, `set_subscription`, `set_subscription_price`, no fee waiver anywhere). The release fee is **2%** on every rail (`fee_bps_public = fee_bps_private = 200`), charged only when a tier executes or a vesting installment is released. A payout in SKR (`mint == config.skr_mint`) pays **1.5%** instead (`fee_bps_skr = 150`), on any rail, and **10%** of that SKR fee (`skr_burn_bps = 1000`) is burned from the vault's token account (the vault PDA signs; event `FeeBurned`); the other 90% goes to the treasury ATA. Withdrawals, closing, cancelling and revoking stay free. The two subscription error variants are kept as `DeprecatedSubscriptionDisabled` / `DeprecatedInvalidSubscription` (6029/6030) so no error code shifts; 6031 `UnsupportedMint` and 6032 `TreasuryAccountRequired` are new. Mentions of the subscription earlier in this report are historical.

Every test that documented a defect now asserts the fix and runs by default: no `#[ignore]` and no `skip:` is left in `onchain/programs/deadman/tests/review_*.rs` or `test/security/offchain_test.dart`.
