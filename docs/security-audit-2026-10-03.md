# Deadman security audit (2026-10-03)

Scope: the Anchor program `onchain/programs/deadman` (devnet `ACHVLMoLDM3YPpGbNST4cZW4Tf2jx6nzJGuusyLJHofL`, 13 instructions) and the off-chain code that holds keys or moves funds: `lib/solana`, `lib/kora`, `lib/rails`, `lib/state`, `lib/wallet`, the Android MWA bridge, `kora/sponsor.toml`, `tool/keeper.dart`.

Method: solana-ai-kit `/audit-solana` checklist (solana-dev `security.md`, Trail of Bits Solana vulnerability scanner, safe-solana-builder). Four independent auditors (program authority, program funds, program lifecycle, off-chain), then one adversarial verifier per lens that tried to refute every finding and wrote a LiteSVM proof of concept for each program finding it could not refute. Unaudited hackathon code; this is not a substitute for an external audit.

## Summary

| Severity | Count |
| -------- | ----- |
| Critical | 0     |
| High     | 2     |
| Medium   | 7     |
| Low      | 11    |
| Info     | 14    |

No finding lets an unprivileged party steal user funds. The two Highs are permanent-loss paths: a token tier that can never pay blocks every later tier for that token (program), and private-rail claim keys can be lost with no recovery (app). The Mediums break core guarantees (a guard-key holder can delay inheritance indefinitely; check-in and duress lockdown can silently skip plans) or let third parties drain protocol SOL (keeper rent, Kora sponsor).

Raw findings: 38 across four lenses, merged here where two lenses found the same bug. Every finding below was confirmed by the verifier; program findings are backed by passing PoC tests in `onchain/programs/deadman/tests/poc_*.rs` (they assert the buggy behaviour, so they will fail once fixed and should be inverted into regression tests).

## H-1 [High] Per-asset rule order plus a push payout to the beneficiary's ATA lets one earlier beneficiary block every later token rule for that mint, permanently

- **Where:** `onchain/programs/deadman/src/instructions/funds.rs:482` (Program); also reported as FUNDS-1
- **Exploit scenario:** The owner sets USDC rules [0] heir A 10%, then [1] heir B 100%. Both use classic SPL Token. Before or after the owner dies, heir A runs SetAuthority(AccountOwner) on their own USDC ATA. Classic SPL Token allows this because its ATAs have no ImmutableOwner. Other ways to reach the same state: the USDC freeze authority blacklists A's ATA; or, on a Token-2022 mint, A turns on RequiredMemo on the ATA (the program never CPIs a memo) or the mint has DefaultAccountState=Frozen. After that, execute_token_rule(0) always fails. beneficiary_token is pinned to ATA(A, mint, token_program) through `associated_token::authority = beneficiary`, so a reassigned ATA trips ConstraintTokenOwner and a frozen or memo-required ATA makes transfer_checked revert. No other account can stand in. Then state.rs:161-166 (check_executable) rejects execute_token_rule(1) for heir B with RuleOutOfOrder, forever. The owner is dead and the guardian has no power over rules, so B's tokens and any later same-mint tiers are frozen in the vault PDA. A gets nothing out of it, but a spiteful heir, a sanctioned heir or an exchange deposit address as beneficiary is enough to trigger it. A PoC test (classic-token SetAuthority and freeze variants) is in the scratchpad but was NOT run because the disk is full (531 MB free).
- **Fix:** Do not hard-pin the destination to the ATA. Accept any token account with `token::mint = mint, token::authority = beneficiary`: anyone can create a fresh non-ATA account for the beneficiary with InitializeAccount3, which gets around reassigned, memo-required and individually frozen ATAs. Also add a skip or forfeit path: if rule i has been due for longer than a grace period (e.g. 30 days) and is still pending, let later same-mint rules run, or switch to a pull model with a per-rule claim escrow. Add LiteSVM tests for a reassigned ATA and a frozen ATA.
- **Verification:** PoCs acct1_reassigned_beneficiary_ata_blocks_later_same_mint_rules_forever and acct1_frozen_beneficiary_ata_blocks_later_same_mint_rules both PASS in onchain/programs/deadman/tests/poc_program_auth.rs. Variant 1: heir A runs classic SPL SetAuthority(AccountOwner) on its ATA, handing it to an unspendable key. execute_token_rule(0) then fails with ConstraintTokenOwner, because beneficiary_token is init_if_needed with associated_token::authority = beneficiary (funds.rs:528-535), and execute_token_rule(1) for heir B fails with RuleOutOfOrder (state.rs:161-166). The vault keeps all 1,000,000 tokens 400 days after the owner goes silent. Variant 2: the mint's freeze authority freezes A's ATA, and the result is the same: rule 0 is rejected as frozen and rule 1 gets RuleOutOfOrder. No instruction can skip a rule, and no role other than the owner can change rules, so B's funds stay frozen for good once the owner is dead. High stays: this is a permanent freeze with a plausible precondition (a spiteful or sanctioned heir, or an issuer blacklist).

## H-2 [High] Claim keys exist only in device secure storage with no backup or export, and 'Forget this device' silently deletes them

- **Where:** `lib/state/secure_store.dart:110` (App)
- **Exploit scenario:** A beneficiary creates a Cloak or Zcash receiving profile (secure_store.dart:96-104 generates a random Ed25519 claim key and stores it only in FlutterSecureStorage). The owner writes the claim key address into a rule as its beneficiary. Later the beneficiary taps Settings > 'Forget this device', whose text says only 'Deletes PINs and the guard key' (settings_tab.dart:149-151). That calls SessionController.reset (providers.dart:65-69), which runs SecureStore.wipe() = _storage.deleteAll() and so destroys every claim_* key as well. Uninstalling, a factory reset, or replacing the phone has the same effect. Nothing in lib/ exports or backs up a claim key: grep finds no export, backup or mnemonic path, and the only sharing is the public claimCode. If the owner has died, which is the case the product exists for, nobody can update the rule. Anyone can still execute it (execute_sol_rule / execute_token_rule), and the payout lands on a key whose secret is gone. The inheritance is permanently lost.
- **Fix:** Derive claim keys from a backed-up secret, such as a mnemonic shown at profile creation or a key derived from a signature by the beneficiary's Seed Vault wallet, so they can be recovered on a new device. At minimum, make reset() delete only the PIN and guard entries, and warn and block while claim profiles exist or claim keys hold a balance.
- **Verification:** lib/state/secure_store.dart:96-104 makes the claim key with Ed25519HDKeyPair.random() and stores it only in FlutterSecureStorage. secure_store.dart:110 wipe() = _storage.deleteAll(), which removes the claim_* entries too. providers.dart:65-69 reset() calls wipe(). settings_tab.dart:149-161 'Forget this device' calls reset(), and its subtitle says only 'Deletes PINs and the guard key'. A grep of lib/ for export, backup or mnemonic finds no recovery path; the only thing shared is the public claimCode (secure_store.dart:27). The rule's beneficiary is fixed on-chain (funds.rs:242-252), so after the owner dies anyone can still execute the rule, and the payout goes to a key nobody holds. Losing or replacing the phone, or uninstalling the app, has the same effect. These are plausible preconditions over an inheritance time horizon, so High stands.

## M-1 [Medium] Guard key alone can postpone inheritance forever; pulse is only blocked once every rule has executed, including after a partial release

- **Where:** `onchain/programs/deadman/src/instructions/vault.rs:131` (Program); also reported as ACCT-2
- **Severity:** reported High, set to Medium by the verifier
- **Exploit scenario:** The owner dies or is incapacitated. Someone holds the guard key: a thief, or a family member who has the unlocked phone, since the biometric gate is only in the UI and the key sits in app secure storage. Kora sponsors guard pulse and lockdown txs, so for that person each `pulse` costs nothing. Because `Pulse` accepts `signer == vault.guard` and `handle_pulse` only rejects when `is_completed()`, they call `pulse` before the earliest pending `after_secs` runs out, and every pending rule's `rule_due_at = last_pulse + after_secs` moves forward again. This works even after tier 0 has already executed, which shows the guard was silent. No one else can step in: the guardian cannot revoke the guard and beneficiaries have no challenge path. PoC poc_guard_blocks_inheritance_indefinitely blocks tier 1 for 3800 days of simulated time while tier 0 had already paid out. Funds stay frozen for as long as the key holder wants, which gives them leverage to extort the heirs.
- **Fix:** Track owner liveness separately from guard pulses. Add `last_owner_seen`, updated only by owner-signed instructions. Cap guard-only extension, e.g. a rule is due at min(last_pulse + after_secs, last_owner_seen + after_secs + MAX_GUARD_EXTENSION), or allow at most N guard pulses per owner signature. Also reject guard-signed pulses once any rule has executed, so only an owner signature can stop later tiers. Optionally let the guardian revoke the guard after the owner has been silent for interval_secs.
- **Verification:** poc_guard_blocks_inheritance_indefinitely (PASS): tier 0 executes, then a guard-only pulse every 19d for 200 cycles (~10.4 years) keeps tier 1 RuleNotDue, and the vault balance does not change. Code path: the Pulse constraint accepts signer==vault.guard (vault.rs:125-127). handle_pulse rejects only on is_completed() (vault.rs:134, state.rs:110). rule_due_at = last_pulse + after_secs (state.rs:125). This is deliberate: the existing test pulse_resets_pending_rules_after_partial_release relies on it. Downgraded from High to Medium. Nobody gains funds and nothing goes to the attacker. The freeze needs the guard key to be compromised and lasts only while the attacker keeps pulsing. It is a broken core guarantee (inheritance can be vetoed by whoever holds the guard key) rather than theft. The client pulse is a manual button (pulse_tab.dart:197), not an automatic pulse.

## M-2 [Medium] Percent rules compound on the remaining balance and leftovers have no sweep; the app shows them as 'X% of SOL', so typical splits strand funds permanently

- **Where:** `onchain/programs/deadman/src/state.rs:237` (Program + app)
- **Exploit scenario:** rule_gross applies Percent to the asset's balance when the rule executes, and per-asset order is enforced, so the percentages compound. The owner sets 50% SOL to Alice and 50% SOL to Bob, which the app displays as '50% of SOL' (lib/ui/rules_format.dart:33-34) with no warning and no check on the sum in rules_editor. Alice gets 50%, Bob gets 25%, and 25% stays in the vault. Once every rule has executed, only the owner can withdraw (withdraw_sol/withdraw_token need the owner signature) and pulse is rejected with PlanCompleted, so for a deceased owner the residual is lost permanently. The same applies to Percent rules that sum to less than 100%, to Fixed rules smaller than the balance, and to any assets deposited later (airdrops, incoming payments) after the last rule for that asset has executed.
- **Fix:** Choose one semantic and make the program and UI agree. Either define Percent as a share of a snapshot taken when the first rule for that asset executes (store the snapshot per mint on the vault), or keep compounding and have the client convert the intended shares (A 50% of total, B 50% of total gives A=5000 bps and B=10000 bps of the remainder). Validate in the client that the last rule per asset takes 100% of the remainder, or add an optional on-chain residual beneficiary that can sweep after all rules execute.
- **Verification:** Proved by poc_funds2_percent_compounds_and_residual_is_stranded. With two 50% SOL rules and 10 SOL, Alice gets 5 SOL minus fee, Bob gets 2.5 SOL minus fee, and 2.5 SOL (25%) stays withdrawable. is_completed() is true, pulse fails with 6015 PlanCompleted, and re-executing fails with 6008. Code: rule_gross applies Percent to the live balance (state.rs:237-247), the order is enforced, and withdraw_* needs the owner signature. The doc comment at state.rs:45 does describe compounding, but lib/ui/rules_format.dart:33-34 shows the rule as 'X% of SOL', so the program and UI disagree. Medium is kept.

## M-3 [Medium] Keeper pays ATA rent for attacker-chosen token-rule beneficiaries; an attacker can loop update_policy and pocket the rent

- **Where:** `tool/keeper.dart:51` (Keeper / program)
- **Exploit scenario:** The attacker creates one vault, deposits nothing, creates the vault's ATA for any classic SPL mint, and sets 8 token rules (Fixed amount 1) to 8 fresh beneficiary keys with after_secs = interval + 60 (about 120 s). keeper.sweep executes every due rule without any profitability check (keeper.dart:50-58). executeRuleIxs (codec.dart:583) makes the keeper pay create-idempotent for the treasury ATA. execute_token_rule then runs `init_if_needed, payer = executor` on beneficiary_token (funds.rs:246-247). rule_gross returns min(amount, 0) = 0, so a zero transfer succeeds and the fee is 0. Each execution costs the keeper about 2.04M lamports of ATA rent. The attacker owns the beneficiary keys, closes the empty ATAs and collects the rent. update_policy (vault.rs:77-95) marks every rule pending again, so one vault can repeat the cycle every few minutes for only tx fees. That is roughly 16M lamports per cycle moved from the keeper wallet to the attacker until the keeper is empty.
- **Fix:** Keeper: skip token rules whose beneficiary ATA (and the treasury ATA) do not exist unless the protocol fee covers the rent, and skip rules whose computed gross is 0. Program option: have the vault pay the beneficiary-ATA rent from its own lamports (or require the ATA to exist), and reject zero-amount executions.
- **Verification:** tool/keeper.dart:48-58 executes every rule for which canExecute (deadman_api.dart:121-128) is true. It never checks whether the payout is profitable or zero. codec.dart executeRuleIxs makes the keeper (executor) pay createAtaIdempotent for the treasury ATA. funds.rs:245-252 has beneficiary_token as init_if_needed with payer = executor. state.rs:237-240 rule_gross caps at the balance, so the result can be 0, and funds.rs:32-34 vault_transfer returns Ok for amount 0. state.rs:191-192 only requires Fixed amount > 0 at policy time. vault.rs:77-95 update_policy resets executed_at to 0 (state.rs:219-231), and a rule can come due after interval+60 = 120 s (constants.rs). The attacker owns the beneficiary keys, so they can close the empty ATAs and recover about 2.04M lamports each. The keeper executes at most one rule per vault per sweep (keeper.dart:65 break), but many vaults or plan_ids scale the attack. One limit: the attacker must create the vault ATA once, and that one is not recoverable. Medium is right because the loss is bounded to the keeper wallet.

## M-4 [Medium] Kora sponsor can be drained or saturated: the usage limit is skipped for Kora-only-signed transactions and is per-key (Sybil), any Deadman/ComputeBudget transaction qualifies, and the node has no auth on 0.0.0.0

- **Where:** `kora/sponsor.toml:21` (Kora sponsor); also reported as ACCT-5
- **Exploit scenario:** In kora-lib 2.0.5, usage_tracker.rs:131-136 returns Ok(None) when every signer is a Kora signer, and check_transaction_usage_limit (line 214) then skips the limit entirely. So a transaction whose only signer is the Kora fee payer, with a single ComputeBudget instruction (an allowed program, sponsor.toml:49-52), passes validate_transaction (non-empty instructions, at most 2 signatures, allowed programs, no fee-payer outflow) and is signed and sent with no counter at all. Each such transaction can cost up to max_allowed_lamports = 50,000 (5,000 base + 45,000 priority). Alternatively, a fresh keypair per 1,000 transactions defeats the per-wallet counter, and any no-CPI Deadman instruction such as execute_sol_rule or pulse on the attacker's own vault also qualifies. The node listens on 0.0.0.0:8080 (confirmed by ss) with no api_key or HMAC. At the global rate_limit of 20 rps, up to about 1M lamports per second, the 0.5 SOL fee payer is empty in minutes. Even without draining it, 20 rps of junk starves legitimate pulses. Once the sponsor is empty or saturated, the app's guard-key pulse and lockdown fail: with a sponsor configured, the guard holds no SOL (deadman_client.dart:335-337), and the UI never uses buildPulseByOwner as a fallback. Owners then cannot check in from the app and their rules can fire while they are alive.
- **Fix:** Put an authenticated backend in front of Kora (HMAC secret held server-side, binding requests to registered guard keys), or move to a Kora version or policy that requires a non-Kora signer and checks instruction discriminators (pulse/lockdown only). Bind the node to localhost or a VPN. In the app, fall back to a guard-paid or owner-signed (buildPulseByOwner) pulse and lockdown when the sponsor fails.
- **Verification:** In kora-lib-2.0.5, src/usage_limit/usage_tracker.rs:120-136 extract_transaction_sender returns Ok(None) when every signer is a Kora signer, and check_transaction_usage_limit (lines ~212-218) skips the check when sender is None. validate_transaction (validator/transaction_validator.rs:97-122) checks only for non-empty instructions, the signature count (≤2), allowed programs, disallowed accounts and fee-payer usage. A transaction containing only a ComputeBudget instruction therefore passes. sponsor.toml:21-25 sets the limit per wallet (Sybil-able), and allowed_programs at lines 49-52 includes ComputeBudget and every Deadman instruction. `ss` shows kora listening on 0.0.0.0:8080. kora/.env has no non-empty SPONSOR_API_KEY, so kora_start.sh:64 starts the node with no API key. deadman_client.dart:333-337 skips funding the guard when a sponsor is set, and _sendWithKey (lines 704-735) has no fallback. buildPulseByOwner (deadman_client.dart:472) is never called from lib/state or lib/ui. Severity stays Medium: the direct loss is the sponsor's float, and rules still need the owner to stay silent for after_secs. The owner's wallet-signed actions also call record_pulse, which limits how much harm the lost liveness causes.

## M-5 [Medium] Duress and Panic lockdown fail silently or report false success; plans with a different guard are skipped

- **Where:** `lib/state/actions.dart:122` (App)
- **Exploit scenario:** VaultActions.lockdown returns without error when the guard key is missing (line 124) or when no plan's on-chain guard equals this device's guard (lines 127-129). The Panic tile in settings_tab.dart wraps it in runGuarded with success: 'Vault locked down', so after 'Forget this device', or after creating a new plan with a new guard without rotating, the user is told the vault is locked when nothing was sent. Plans whose guard differs are silently left unlocked. On the duress path, lock_screen.dart:30 runs `unawaited(lockdown().catchError((_) {}))`, which swallows every failure: sponsor drained or unreachable (OFF-3), RPC 429, no owner in session, or blockhash expiry. There is no retry and no owner-signed fallback, even though the program's Lockdown accepts the owner as signer. The coercer can then use the coerced Seed Vault approval outside the app to withdraw from vaults that were never locked, which breaks the duress guarantee.
- **Fix:** Treat 'no guard' or 'no matching plans' as errors in lockdown. Lock every plan of the owner and report the ones the guard cannot sign for. On duress, retry with backoff (persist a pending-lockdown flag and retry from WorkManager) and fall back to a guard-paid transaction when Kora fails.
- **Verification:** actions.dart:122-132: lockdown() returns silently when the guard is null (line 124) or when no plan's guard matches (lines 125-129), and it only locks plans whose guard equals this device's guard. settings_tab.dart:98-102 wraps it in runGuarded with success 'Vault locked down', so the user gets a false success. lock_screen.dart:30 runs `unawaited(...lockdown().catchError((_) {}))`, which swallows every failure without retry. The owner-signed path that the program accepts (vault.rs:149-151) is never used as a fallback. Exploiting this still needs the coercer to get a Seed Vault approval, which is the threat model duress mode exists for. Medium is right.

## M-6 [Medium] "I'm alive" silently skips plans guarded by another key, yet reports success on all active plans

- **Where:** `lib/state/actions.dart:108` (App)
- **Exploit scenario:** pulse() pulses only plans with `v.guard == guard.address` (line 108). The success toast in pulse_tab.dart:202-204 says 'Pulse recorded on N plans', where N counts every non-completed plan (pulse_tab.dart:90,159). After 'Forget this device', createVault calls createGuard() (actions.dart:79) and gives new plans a fresh guard, while older plans keep the old guard. The settings text asks the user to rotate, but nothing enforces it. Every check-in then skips the old plans while the user is told all of them were pulsed. Their rules become executable by anyone, so funds are released to beneficiaries while the owner is alive. If no plan matches, the error shown is the misleading 'Every plan has fully released'.
- **Fix:** Compute the plan set from all active plans. For any plan whose guard is not this device's, fail loudly and offer rotateGuard or an owner-signed buildPulseByOwner. Report the exact set of plans pulsed.
- **Verification:** actions.dart:106-109 pulses only plans that are not completed and have v.guard == guard.address. pulse_tab.dart:90 counts active as every non-completed plan and passes it to _PulseButton (line 159). The success toast at lines 199-204 reports 'Pulse recorded on ${activePlans} plans'. actions.dart:79 createVault uses loadGuard() ?? createGuard(), so after reset() a new plan gets a fresh guard while old plans keep the old one, and nothing enforces rotateGuard. No UI code compares plan guards against the device guard (a grep for .guard finds only actions.dart). When no plan matches, the misleading error 'Every plan has fully released' appears (lines 110-113). The result is false assurance that can let rules fire while the owner is alive.

## M-7 [Medium] Duress PIN session leaves claim-key funds fully spendable: claim destination can be changed and routed with no decoy and no biometric

- **Where:** `lib/state/actions.dart:202` (App)
- **Exploit scenario:** A coercer makes a beneficiary open the app with the duress PIN, which unlocks the full UI (lock_screen.dart:27-30). saveClaimProfile (line 202) and routePrivately (line 217) are not wrapped in _decoy and have no _biometric check. For Cloak, any base58 32-byte Solana address is accepted as destination (cloak_route.dart:245-246, 'publicRecipient'), with no validation at save time. The coercer sets the Cloak destination to their own Solana address, then taps route. The claim key, a hot key on the device, signs the deposit and withdrawal, and the beneficiary's inherited SOL leaves for the attacker. The same works with the normal PIN alone: phone plus 6-digit PIN is enough, with no Seed Vault approval. Mainnet builds only, since the routes are unavailable on devnet.
- **Fix:** Wrap saveClaimProfile and routePrivately in _decoy. Require a biometric check for both, and require it again when a destination changes. Consider a time delay on destination changes, and only allow Cloak shielded addresses or a destination confirmed through the beneficiary's own wallet.
- **Verification:** lock_screen.dart:27-30 unlocks the full UI with the duress PIN. actions.dart:202-214 saveClaimProfile and 217-242 routePrivately are not wrapped in _decoy (lines 271-277) and do not call _biometric. Only Zcash destinations are checked for the u1 prefix. cloak_route.dart:245-246 accepts any base58 pubkey as publicRecipient. The claim key is a hot device key (secure_store.dart:96-104) and signs the route in route.execute. With the phone and PIN, the coercer can redirect the destination and route the claim-key funds. Routing is mainnet-only (cloak_route.dart:217, zcash_route.dart:105).

## L-1 [Low] Rules can be consumed with paid=0 and nothing reserved, which strands residual funds after the owner dies

- **Where:** `onchain/programs/deadman/src/instructions/funds.rs:428` (Program); also reported as FUNDS-3, SM-3
- **Exploit scenario:** In execute_sol_rule, if beneficiary.lamports() + net < rent.minimum_balance(beneficiary.data_len()), the code sets net and fee to 0 but still sets executed_at. A beneficiary can allocate data on their own account and so forfeit at will, or a fresh claim key receives a small Percent or Fixed payout. In both cases the rule is permanently spent. If it was the last SOL rule, the SOL stays in the vault forever, and pulse is rejected once the plan is complete. execute_token_rule behaves the same way: if anyone has created the vault ATA (permissionless), a due token rule with balance 0 can be executed by anyone, consuming it at paid 0. Tokens deposited later, such as airdrops or late transfers, are then stranded.
- **Fix:** Revert (or leave the rule pending) when the gross amount is 0 or the payout cannot be delivered, instead of marking it executed. Alternatively, send undeliverable dust to the next pending rule for the same asset, or make the last rule sweep the remaining balance.
- **Verification:** PoCs acct4_sol_rule_consumed_with_zero_payout_strands_funds and acct4_token_rule_consumed_with_empty_balance_strands_later_deposit PASS. SOL case: a Fixed 100,000-lamport rule to a fresh key goes through the rent branch (funds.rs:473-479), which zeroes net and fee, yet the rule is still marked executed with paid=0 (funds.rs:489-490). The beneficiary gets 0, more than 2 SOL stays in the vault, and pulse then returns PlanCompleted. Token case: the vault ATA exists with 0 balance, the rule executes with paid=0 because vault_transfer skips amount 0 (funds.rs:315-317), and 500,000 tokens minted later cannot be claimed (RuleAlreadyExecuted). The amounts involved are dust, or depend on the beneficiary's own choice or on a 0 balance, so Low.

## L-2 [Low] update_policy re-arms executed rules (executed_at=0), and the official editor resends executed tiers, so beneficiaries get paid twice

- **Where:** `onchain/programs/deadman/src/state.rs:228` (Program + app)
- **Severity:** reported Medium, set to Low by the verifier
- **Exploit scenario:** Vault rules: [A Fixed 1 SOL @10d, B Fixed 1 SOL @20d]. The owner is away and tier 0 pays A. The owner returns and opens the rules editor to rename the plan, change cadence or remove a rogue guardian. The guardian can only be removed through update_policy. rules_editor.dart:138-140 loads every on-chain rule, executed ones included, and `_save` resubmits them. `apply_policy` rebuilds every Rule with `executed_at: 0, paid: 0`. On the next 10-day silence anyone executes index 0 again and A is paid a second time. PoC poc_update_policy_rearms_executed_rule_double_pay: A balance 0.98 SOL -> 1.96 SOL. The program offers no way to change the label, interval, lock or guardian without resetting all rule history. The PolicyUpdated event does not show that tiers were re-armed.
- **Fix:** In update_policy, keep executed state. Either reject inputs whose rule count or order conflicts with executed rules, or carry executed_at/paid forward for indices already executed (store a policy-version hash). Better still, split guardian, label and cadence changes into a separate instruction that does not touch rules. In the client, filter executed rules out of the drafts, or show them read-only.
- **Verification:** poc_update_policy_rearms_executed_rule_double_pay (PASS): A receives 0.98 SOL, the owner resubmits the same rules, rules[0].executed_at becomes 0, and after another 10 days of silence A receives another 0.98 SOL (1.96 total). Code: apply_policy rebuilds every Rule with executed_at:0, paid:0 (state.rs:205-216). rules_editor.dart:138-140 loads every on-chain rule into the drafts, executed ones included. Downgraded from Medium to Low. It needs an owner-signed update_policy, the documented behavior is 'Replaces every rule (all pending again)' (vault.rs:72), and the second payment needs the owner to go silent again. The loss comes from the owner's own funds through a UX footgun, not from a third party. The real problem is that the guardian/label/cadence changes are coupled to the rule reset, together with the client resending executed tiers.

## L-3 [Low] set_guard allowed during lockdown lets an owner-key holder disable the device's ability to extend the lockdown

- **Where:** `onchain/programs/deadman/src/instructions/vault.rs:100` (Program)
- **Exploit scenario:** A thief or coercer controls the owner key (Seed Vault). The device guard calls lockdown, which freezes withdraw for lock_secs and can be repeated without any rate limit. While the vault is locked, the attacker calls set_guard(attacker_key), which is explicitly allowed during lockdown. The legitimate device can no longer re-lock. The guardian is rate-limited by guardian_ready_at, so it cannot cover the gap. When locked_until passes, the attacker calls withdraw_sol and withdraw_token. Lockdown therefore guarantees exactly one lock_secs delay, not a freeze the device can keep renewing. The design comment chooses this to defeat a stolen guard, but the trade-off is undocumented, and an owner-key thief turns it to their advantage.
- **Fix:** During lockdown, either require the guardian to co-sign set_guard, or let the new guard take effect only after locked_until. Or document plainly that lockdown is a single bounded delay against owner-key compromise.
- **Verification:** PoC acct3_set_guard_during_lockdown_strips_device_relock PASSES. The guard locks the vault and withdraw returns VaultLocked. The owner-key holder's set_guard succeeds while the vault is locked, since handle_set_guard has no require_unlocked (vault.rs:100-112). The old guard's next lockdown fails with Unauthorized. The guardian can extend the lock once, then hits GuardianCooldown (vault.rs:170-179), and after that withdraw_sol drains the vault. ## L-4 [Low] Cross-asset stipend ordering lets the executor choose which beneficiaries receive vault SOL, and the stipend is not recorded

## L-10 [Low] Earn deposits the owner's entire JitoSOL balance, and the Jupiter transaction is signed with only a check that the owner is a signer

## L-11 [Low] Confirmation timeout invites a re-tap that can duplicate wallet-signed sends
